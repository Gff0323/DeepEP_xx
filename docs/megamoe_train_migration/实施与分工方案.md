## 3. 名称与目录建议

### 3.1 推荐名称：`megamoe_train`

目标仓现有对外实验模块叫 `experiments/megamoe`，其中设备目录另有 `csrc/kernels/mega_moe`。本次所说的“同级”建议指 **`experiments/` 下的模块层**，不是只在推理 kernel 内部增加训练文件夹。

| 名称 | 评价 |
| --- | --- |
| `megamoe_train` | 推荐；与现有模块名风格一致，明确是训练，容纳 BF16/W8A8 |
| `mega_moe_train` | 可理解，但与同级 `megamoe` 的拼写风格不同 |
| `megamoe_bf16` | 不推荐作为训练模块顶层，容易把未来 W8A8 变成另一个孤立模块 |
| `megamoe_v2` | 不推荐，不能表达训练/推理职责，也容易误解为替换旧实现 |

Python 命名空间为 **`deep_ep_experimental.megamoe_train`**，与 `deep_ep_experimental.megamoe` 并列。首批公共类名可沿用 `MegaMoeBF16Train`，保留类名和训练语义；构造入口适配目标 runtime，实施后记录实际接口。

## 5. 开工前共同冻结的五个交接契约

### C1：公共前后向语义

建议保持 `forward(x, topk_ids, topk_weights, w1, w2, max_recv_tokens, ...) -> (y, counts)` 的使用形态和 autograd 体验，具体类构造、参数归属和底层绑定需确认。

| 项目 | 必须明确 |
| --- | --- |
| 路由和输入 | `x`、路由概率、权重为当前源语义要求的 BF16，ID 为 int32；shape/连续性/合法 TopK 规则写清 |
| 权重布局 | 保留源支持的 canonical/legacy 布局及其识别，不在外围默默增加转置或复制 |
| 保存模式 | 四模式解析、`auto` 选择、clipping/clip mask、原有舍入点与默认值 |
| 输出/梯度 | `y/counts`；四项梯度分别返回；不可微量明确处理 |
| 诊断能力 | 公共调用保持简洁；诊断 holder/debug 作为私有入口评审，不能删掉必要同步 |

### C2：Host/Device ABI

由你说明并提供参数结构、字段类型/对齐/大小、launch/export 名称、返回值、版本和能力查询。框架调用按同一份契约实现；不独立手写第二套结构或按旧 SO 猜测字段。

迁移首轮保持布局和计算语义；若必须改变 ABI，明确版本与检查。构建时及运行时应能发现 Python、Host、kernel 不匹配，而不是静默运行旧库。

### C3：saved state 与 workspace

| 资源 | 所有者/用途需约定 | 释放或复用条件 |
| --- | --- | --- |
| SHMEM owner | 根 Runtime/Session 唯一 owner，训练实例借用其窗口 | 所有相关算子关闭、异步任务完成后，各 rank 同序显式释放 |
| 训练通信窗口/context | 训练实例持有；你提供布局/协议要求 | 当前消费者退休后才能复用，不以 Python forward 返回为完成证据 |
| `training_saved_state` | 每次 forward 的 autograd 上下文持有 | 对应 backward 完成；不同 forward 不串用 |
| `dispatch_output` | 当前反向依赖的独立 Tensor | 按源语义保留到反向；不公开无法完成反向的释放选项 |
| forward transient scratch | 本次 forward 临时资源 | 设备实际使用完成后释放，不无条件放入长期 saved state |
| backward workspace | 对应 backward 的资源 | kernel 使用完成后释放；异步 allocator 需正确保活 |

### C4：公共运行时与训练窗口

目标仓当前有进程级 SHMEM owner 排他检查；推理 MegaMoE 专用 Session 的现有限制是 EP≤128、对称工作区≤1 GiB。源训练路径另有容量、context 和窗口语义。

**本轮已实现复用根 owner，增加训练专用 Session 工厂，由训练实例管理借用窗口的 context。** 推理原有限制保持不变。训练初始化选择 MTE，与源测试的 UDMA engine 选择不同；目前只有单机验证，多机传输及 EP 子组必须由第二阶段专项复核。

不能直接复制源 `ShmemInstance` 后与目标 Session 各自初始化，也不能简单放宽推理 Session 的上限来冒充训练接入。应分别明确训练容量、EP、窗口数和资源 API，并验证不破坏现有推理/通信。

首批是否承诺多个训练实例、microbatch 交错、跨 stream、训练/推理同进程共存，需按实际框架需求定义。没有验证的并发方式不自动承诺。

### C5：验收与错误处理

精度阈值、shape/EP/路由矩阵、warmup/测量次数、性能接受标准、超时与失败日志先写清。每个输出和梯度独立判定，保留失败项及未测项；不能只看 loss 或成功返回。

## 7. 验证怎么分工、看什么证据

### 7.1 精度与功能

首轮由你迁移并执行独立 CPU 高精度/PyTorch 小算子参考和 runner，第二阶段同事独立复核；你复核数学、舍入、量化和 clip mask 规范。参考实现不直接调用被测 kernel 作为标杆。

- 前向 `y`、expert counts，反向四项梯度，包含非单位上游梯度。
- `bf16 / none / mxfp8 / auto` 与 clipping 的合法组合；跨保存模式按各自数值语义判定，不一律要求逐位相同。
- 两种源权重布局；典型 shape、对齐边界、空专家、均衡/固定种子随机/倾斜路由、容量不足和非法输入。
- 更换输入重复调用、多次 forward 后 backward、关闭顺序、已关闭对象调用；多实例/跨 stream 按实际承诺范围验证。
- 保留 b8cff148 中已整理的自包含 MXFP8 保存格式参考，检查迁移后不再引用已删除 W8A8 golden/旧头；不恢复整个 W8A8 算子或删除必要模式测试。

### 7.2 性能、显存与稳定性

首轮由你完成测量与分析，第二阶段同事独立复测，双方确认比较口径。

- 先精度后性能；同机、同输入、同路由/seed、容量和编译策略，记录实际加载的 Host 与 kernel SO。
- 使用原版→候选→候选→原版等配对顺序；正式性能关闭 Timer/debug，前向、反向、完整调用分别测量。
- 保留各 rank 原始样本、p50/p95 和长尾；不只挑有收益的场景。完整调用不以局部阶段相加替代。
- 显存区分持久 SHMEM、saved state、dispatch output、transient scratch 和峰值占用。
- 长循环、资源创建/释放、异常退出和超时均留证；循环次数和稳定性时长由双方事先约定。
- 设备启动前核对健康与占用；使用独立工作区、库路径及适当隔离环境，不终止别人的任务。

### 7.3 打包与目标仓回归

首轮由你完成构建与回归，第二阶段同事从干净环境独立执行。
